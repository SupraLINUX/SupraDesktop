# Estrategia de licencias
Estado PROPOSED. Recomendación: GPL-3.0-or-later para código propio del escritorio y componentes de distribución que adapten GPLv3, SDK independiente MIT/Apache-2.0 si realmente necesita integración permisiva y no deriva de GPL, documentación y arte según licencia explícita por archivo. No elegir LICENSE sin ratificación. No relicenciar terceros ni convertir GPL-3.0-only en or-later por decisión propia.
Fuentes: [GNU license compatibility](https://www.gnu.org/licenses/license-compatibility.html), [Apache GPL compatibility](https://apache.org/licenses/GPL-compatibility.html), [GNU FAQ](https://www.gnu.org/licenses/gpl-faq.html), [cargo-deny](https://github.com/EmbarkStudios/cargo-deny). Apache-2.0 permite incorporación compatible a GPLv3, no GPLv2-only; MPL-2.0 requiere revisar condiciones de Secondary Licenses y archivos afectados; Linux kernel GPLv2-only separado no obliga por sí mismo a licenciar apps igual. No asumir procesos separados resuelven toda cuestión de obra derivada. 
Metadata GitHub consultada: Smithay MIT, Iced MIT, libcosmic MPL-2.0, Niri GPL-3.0, OverShifted/LiquidGlass MIT, shayann07/liquidglass Apache-2.0; Zed y Slint NOASSERTION (revisar crate, features y opción de licencia); Arkdep GPL-3.0. Metadata no sustituye texto de licencia, SPDX por archivo ni auditoría transitiva. Qt y Calamares revisar módulos y versión. WhiteSur GPLv3 y avisos, no recursos Apple; semejanza por sí sola no prueba infracción.
Antes de adoptar: pin commit, LICENSE/NOTICE/SPDX, dependencias build/runtime, features y recursos, fuentes correspondientes, cambios, atribuciones y distribución de binarios; third_party manifest, cargo-deny, SBOM SPDX/CycloneDX y REUSE como candidatos. Distinguir imagen distro como agregación de paquetes de obra derivada; inventario por componente. Firmware/drivers propietarios solo distribuir con derechos. Revisar marca y similitud antes de publicación. Ninguna licencia nueva aplicada.
